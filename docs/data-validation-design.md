# Data validation implementation boundary

Status: internal predicate prototype only. No public command, persisted rule, UI or write enforcement exists. DATA-01 and COR-02 remain open.

A validation rule changes workbook semantics. ADR 0001 requires an explicit new native schema and safe migration before these rules can be persisted or advertised. Generic extensions are not an enforcement boundary: older readers may ignore them. The new internal `validation-rule.ts` is deliberately absent from public exports and does not add fields to schema 3.

## Prototype contract

The current predicate prototype compares typed calculated values without coercing strings to numbers. Numeric/date serial comparisons support equality, inequality and inclusive ranges; list membership is type-sensitive and case-sensitive; text length counts Unicode code points. Empty text and blank cells follow `allowBlank`, while errors fail. A rule records `reject` or `warn`, but the predicate does not implement warning confirmation. Lists are capped at 1,000 items and 32,768 total UTF-16 text units. These semantics and budgets are provisional until independent spreadsheet fixtures and the product interaction contract are reviewed; date epoch, serial limits, formula validation, locale and grapheme behavior are not decided.

The same blank policy applies before evaluating a custom formula: a blank or empty string is accepted only when `allowBlank` is true, and otherwise produces the configured rejection or warning. The formula evaluator is not invoked for those values. This is the provisional OpenSheet policy, not an independent spreadsheet compatibility claim.

The unexported batch prototype checks overlapping rules against supplied staged values, counts rejection and warning violations separately, and caps returned details at 32 while retaining total counts. It validates rule/range inputs and fails on calculation-limit errors in affected cells. Provisional limits are 1,024 rules, 65,536 cells and one million weighted work units, including rule metadata and candidate checks; list membership is indexed once per rule and the work budget charges both the index build and candidate string length; these must be measured and reviewed before any public contract. It does not write data or authorize warnings.

A separate internal range-transform prototype uses half-open coordinates: insertion at/before the start shifts the range, insertion strictly inside expands it, and insertion at the end leaves it unchanged. Deletion removes affected membership and drops a fully deleted range. A seeded independent membership model checks these provisional semantics for both axes. They are not yet wired into structural commands or native serialization and are not claimed as spreadsheet interoperability.

The internal collection model now validates unique rule identities, strict entry/range fields, actual sheet dimensions and a one-million-unit metadata budget; it preserves overlapping rules and clones validated input. Its structural transform applies the same range behavior across a collection and drops fully deleted entries. Batch checking uses this common model. These remain provisional implementation pieces, not a public or persistent rule system; the budgets and overlap policy need end-to-end performance and product review.

The collection model rejects syntactically malformed formula rules before staging reads or formula evaluation. Duplicate expressions are parsed once per validation call. Syntactically valid unknown functions and `#REF!` remain representable; this check does not assert that a formula evaluates successfully or is compatible with another spreadsheet.

An internal in-memory migration prototype validates a complete schema 3 object, adds empty rule collections in provisional schema 4, and allows conversion back only when no rules would be lost. It validates both formats and rejects malformed or unsupported fields; existing public readers still reject schema 4. Downgrade counts identities from already validated axis runs without expanding them again, and clones the workbook only after confirming that conversion will preserve its semantics. A successful conversion still clones the whole workbook with the costs measured below. The prototype does not create a backup, migrate IndexedDB, preserve engine history, enforce rules, or publish a head.

## Migration sizing (2026-11-10)

On Apple M4, macOS (Darwin 25.5.0), Node 22.19.0, three fresh processes per direction converted a rule-free dense numeric workbook. Run `node --expose-gc scripts/benchmark-validation-migration.mjs 31250 upgrade 32` for 1m cells or use `62500 upgrade 160` for 10m; replace `upgrade` with `downgrade` for the reverse path. The initial 10m fixture (312,500 × 32) was rejected by the 100,000-row limit and was replaced before timing.

## Integration requirements

An internal range bridge can enumerate and deduplicate cells directly intersecting supplied changed rectangles and validation rules, then run the staged checker against the supplied immutable head. It bounds range count, candidate count and intersection work and can yield during enumeration. This is only a direct-change primitive: formula dependencies and changes on other sheets can affect validation outside those rectangles, so it must not be used as complete write enforcement without dependent enumeration. It is not connected to persisted rules or the command pipeline.

The staged batch adapter periodically yields during its rule/cell pair scan, including disjoint ranges, and during position validation, so cancellation can be observed without waiting for a covered cell or the last candidate. Candidate positions are copied synchronously first to prevent caller mutation across yields; rule validation is also synchronous. Tests force the yield deadline and exercise abort and retry in real Workers across three browsers; they do not establish a real-device latency bound.

The engine bridge now supplies the actual sheet dimensions to that same checker instead of synchronously revalidating every position first. Rules and positions are still validated against the actual sheet before staged cell reads; a real-Worker test cancels before a late out-of-sheet position, confirms that retry rejects it, then corrects it and retries without changing the revision. Rule parsing and the initial position snapshot remain synchronous, and the bridge is still not invoked automatically by write commands.

After validating rules, the batch checker computes their enclosing rectangle. A candidate outside that rectangle cannot match any rule, so it skips individual range checks while still charging the original rule/candidate work budget and maintaining cancellation checkpoints. A seeded independent model compares overlapping and disjoint numeric rules, report order and reader calls; paired local Worker measurements and their limits are recorded in [performance](performance.md). Candidates inside the enclosing rectangle still scan every rule; this is not a general spatial index or production enforcement.

The staged batch adapter accepts candidate positions and an async reader over a stable staged revision. It reads only positions covered by a rule, once per position even when rules overlap, and shares the synchronous evaluator's budgets and reporting semantics. Before awaiting reads it snapshots the bounded candidate positions and validated rules, so caller mutations cannot change which cells or rules the check uses. Cancellation or a calculation limit rejects the entire check. The caller must provide a stable revision, enumerate affected positions (including formula dependents where required), and discard staging on rejection; this adapter is not called by the engine yet.

Cancellation also stops waiting for a pending staged read or custom formula evaluation, with late rejection observed. It cannot forcibly stop a caller-owned promise: an integrating reader must honor the signal or coordinate any outstanding work before reclaiming resources. Three-browser dedicated Worker tests cover cancellation of a stalled read; this is not yet a durable transaction cancellation test.

The engine now has a private cell reader bound to an explicit head and metadata pair. Sort and filter calculations use this staged reader; filter recalculation no longer temporarily replaces the engine's live head or metadata. This supplies a building block for a validation reader but does not itself freeze a mutable head, enumerate dependent cells, enforce rules or publish a validation result.

An internal engine bridge now binds a validation session to a supplied head and metadata, verifies rule ranges and candidate positions against the actual sheet, and uses the staged reader and date system for cross-sheet calculations. It is deliberately not called by the command pipeline. In real IndexedDB Workers in Chromium, Firefox and WebKit, a test intercepts publication after two staged writes and verifies that validation sees the new values while a separate committed-view check and the live workbook still see the old values. A unit test also checks invalid positions and pre-aborted requests. The supplied head and metadata must remain stable for the entire check: in particular, the engine reuses and mutates the previous head's block directory after publication, so holding that object after commit is not a historical snapshot. The caller must await validation before publication and prevent other mutation. Rule persistence, affected-dependent enumeration, warning approval, transaction enforcement and post-staging fault tests remain open.

A separate in-process storage test injects a caller rejection after the bridge reports a violation and before head publication; revision, charged bytes, undo availability and cell value remain unchanged after reopen. This exercises one simulated caller and storage implementation, not production rule enforcement or the complete real-Worker fault matrix.

The corresponding [three-browser Worker test](../tests/e2e/validation-staged-rollback.spec.ts) injects a rejecting caller and an aborted validation after a staged read has loaded but before its result is returned. In both cases it compares raw head bytes, record/size/scratch keys, revision, charged bytes, undo availability and the committed value; reopening and retrying the edit also succeed. The cancelled read's injected late promise rejection is observed without an unhandled rejection. The test does not simulate a still-pending IndexedDB request, Worker termination, every transaction write path or actual production rule enforcement.

A separate [termination test](../tests/e2e/validation-staged-termination.spec.ts) pauses a simulated validation reader before its read, verifies that staged record and size keys exist while head bytes remain unchanged, and then terminates the actual Worker. In Chromium, Firefox and WebKit, reopening recovers the prior head, value, bytes, undo state and original record/size/scratch keys; a subsequent edit and undo succeed. This covers one termination point with a simulated stalled reader, not a pending IndexedDB request, actual validation enforcement or the complete transaction fault matrix.

Custom formulas now have an internal rule shape and an evaluation request carrying the target coordinates and offsets from the range's top-left cell. Only boolean `true` passes; an allowed blank skips evaluation, other results fail the rule, and `#LIMIT!` aborts the whole check. A formula evaluator is required for covered, non-exempt cells and must apply reference offsets and a shared calculation budget against the staged revision. This is a provisional contract; structural formula rewrites, persistence, and external spreadsheet parity are unverified.

`AsyncCalculation.validationSession` can evaluate these requests using the same asynchronous evaluator as ordinary cells. It offsets relative reference components, preserves absolute components and sheet qualifiers, and shares a one-million-step counter across candidate reads, rule evaluation and formula dependencies on all sheets in one session. A separate calculation cache and fresh formula parsing prevent prior-revision cached values or persisted ASTs from contaminating the staged view; the caller must still supply an immutable staged reader. Rule results do not occupy a cell or its cache entry. Create one session per transaction over the staged view and bind readers to individual sheets. The engine still needs to create and enforce this session before publication.

The separate cache uses the parent calculator's configured cache budget (including zero). Relative offsets outside the global row or column limits produce `#REF!` without invoking the staged reader; the reader remains responsible for the actual dimensions of each sheet. Cache allocation remains additional to the parent cache and must be accounted for when the engine integrates a session.

The object migration now checks workbook metadata separately and checks each page's object keys and nesting immediately before decoding that page. It still keeps the input in memory and clones the output. A single 10m-cell follow-up upgrade took 15.54 s with 1,077 MiB process peak RSS; this does not demonstrate a performance improvement over the baseline.

An internal staging path now emits checked pages to an awaited sink, yields between pages when the task budget expires, and returns detached schema 4 metadata only after every page succeeds. Cancellation, a sink error or a late validation error prevents the return of publication metadata; the caller must roll back any staged pages. This path still accepts an in-memory source and does not yet open an IndexedDB transaction, own staging cleanup, or publish a revision.

The reverse staging path shares the same page pipeline. It checks rule collections for every sheet after metadata validation and before the first sink write, and rejects downgrade if any rule would be lost. On a successful rule-free conversion it returns detached schema 3 metadata without cloning all cell pages. It is not a durable rollback protocol.

The internal v4 staging path now validates all sheets' rule collections before the first page sink call and returns detached schema 4 metadata with rules preserved only after every page succeeds. Sink failure, cancellation and late malformed pages prevent metadata return; the caller must discard any staged pages. Three-browser Worker tests exercise valid and malformed rule metadata. This remains an in-memory-source staging primitive: it does not publish a head, restore durable rule semantics, enforce writes or expose a supported schema 4 reader.

Page sinks receive the abort signal and must settle only after their pending write has stopped. The staging function waits for that settlement before returning an abort, so cleanup cannot race a late write from a cooperative sink. The internal `Database.write` can now abort a pending IndexedDB transaction through this signal and waits for its abort; record and ledger writes share that transaction. Three-browser Worker tests inject cancellation immediately after queuing a staged write, verify neither record nor ledger appears, and check a later abort does not undo a committed write. A sink that ignores cancellation can still block indefinitely; durable engine integration, other transaction timings and crash-safe cleanup remain to be implemented and verified.

The same Worker fixture also cancels from the ledger request's success callback after both record and ledger requests have succeeded but before transaction completion. All three browsers roll back both stores; a subsequent write to the same key succeeds and its stored length matches the ledger. This injected transaction timing is not a power-loss or full migration recovery test.

The engine now has an internal, explicit rule-free backup import path for streaming JSON. It reuses the IndexedDB importer: pages may be written to scratch before metadata arrives, but nonempty rules prevent publication and scratch is reclaimed. A rule-free backup is validated and published as schema 3 through the existing head commit. This replaces workbook contents and resets undo history, as ordinary import does; it is not in-place history-preserving migration. The path is not exposed by the Worker RPC or public import, and is exercised in real Chromium, Firefox and WebKit Workers: rule rejection and a head transaction abort preserve the old revision, charged bytes and empty scratch, and retry reopens with both imported pages. Actual Worker termination after scratch commit preserves the old revision; termination after head commit and before acknowledgement recovers both pages of the new revision. Both recoveries clear scratch in all three browsers. Large-file performance and history-preserving migration remain open.

Engine cancellation now reaches the JSON and binary stream readers, including a pending read with no incoming bytes. The migration test stalls a real stream after both pages are staged, then checks source cancellation, unchanged revision and charged bytes, and scratch cleanup. Publication checks cancellation again after directory staging and immediately before the head write; a transaction already submitted can still commit.

The shared staged importer also passes its abort signal to each pending scratch write. Three-browser real Worker tests cancel JSON, binary and rule-free validation backups on the third scratch write after two pages have committed, both before and immediately after the third commit. They verify the expected abort or commit, unchanged raw head/record/ledger/scratch state and charged bytes after cleanup, plus undo/redo, reopen and all three page values after retry. This does not publish rule-bearing schema 4 or cover every failure timing.

An internal staged-validation fault test also terminates a real Worker while its staged-record IndexedDB read is kept active by successive actual requests. In Chromium, Firefox and WebKit, reopening restores the prior head, value and charged bytes, reclaims staged record/ledger keys, and allows a later edit and undo. This injected read stall occurs before head publication; it is not physical power-loss evidence or automatic validation enforcement.

- Introduce independently versioned WorkbookFile, binary metadata and engine head support, with old-reader rejection and a tested backup/upgrade/rollback path per ADR 0001. Validate metadata before publication; preserve existing schema 3 readers and fixtures.
- Define range ownership, overlapping rules, insertion/deletion and sheet-copy transforms, rule editing and undo. Establish finite rule/index budgets and migration behavior before storing metadata.
- Validate the staged transaction, not only the UI: `Engine.applyLocal` handles set, paste, copy and fills; `replaceText` and `sort` use separate staged paths; structural commands transform coordinates. Audit every command, imports, undo/redo and plugin/agent envelopes. Prove invalid bulk writes never publish a partial head.
- Formula rules require revision-bound dependency evaluation and explicit calculation-limit/cancellation behavior. Define whether validation sees the complete staged transaction and how formula results and pre-existing invalid cells behave.
- Warning policy needs a bounded, revision-bound confirmation protocol that cannot silently bypass warnings on API, clipboard or agent paths. An intervening write must invalidate approval; rejection must preserve state and history.
- Add editable controls and typed editors only after shared semantics exist. Accessibility and keyboard/IME checks accompany browser tests. Report or reject XLSX features that cannot be preserved; do not claim Excel parity based on this prototype.

Acceptance requires real Worker/IndexedDB fault tests, schema migration/rollback fixtures, independent spreadsheet comparisons, bounded large-range performance and the complete TODO DATA-01 matrix. Unit tests of the prototype do not satisfy those gates.

The internal range transformer now rewrites the anchor formula for edits on the rule's sheet. If deletion removes the anchor, it first rebases the expression to the earliest surviving cell. Absolute references stay absolute but move with structural edits to their referenced coordinates; deleted local targets become `#REF!`. When the edited sheet differs from the rule owner, the transformer retains the owner range and rewrites only references qualified with the edited sheet name. The engine must still invoke this across all rule-owning sheets. This defines anchor-based behavior; it does not split a rule to preserve each member's pre-edit expression or claim spreadsheet parity.
