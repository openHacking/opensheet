# Verification

## 0.2.0-dev.0 candidate (2026-11-12)

The playground's backup recovery previously deleted a newly restored workbook when its scene reference failed to save after attachment. Recovery now writes the reference before attachment. If that write fails, the unpublished candidate is removed; once the reference has been published, a later failure retains the candidate, releases its writer when unattached and reports its ID. This avoids rolling back a non-atomic localStorage reference or deleting a candidate that another tab may already have opened, at the cost of potentially retaining an unreferenced workbook. The 84-case recovery and scene suite passed in Chromium, Firefox and WebKit, including injected reference and attachment failures, cross-tab reference changes and reopening retained values. An earlier implementation attempted rollback and was replaced after cross-tab analysis. These tests inject failures and do not model all races or physical interruption.

The recovery screen now also offers to open that retained candidate explicitly. Six targeted Chromium, Firefox and WebKit cases passed for attachment failure and a competing reference update; the latter also injects a failed reference write on opening, retries, and verifies the selected workbook survives reload. The action can update the scene reference by user choice, but concurrent localStorage writes remain non-transactional. Earlier recovery descriptions below are historical where their publication order differs from this follow-up.

Opening a saved scene no longer writes its previously read ID back. A controlled test changes the reference immediately after the read and verifies that the open page retains its selected workbook while reload opens the newer reference; it passes in Chromium, Firefox and WebKit. This injected ordering does not prove full cross-tab consistency: initialization, reset and recovery still write non-transactional references. The first test run failed because its setup did not accept the dirty-scene confirmation; the corrected setup passed.

Regular demo reset now constructs a replacement before publishing its reference and preserves the old workbook. Nine targeted Chromium, Firefox and WebKit cases cover successful reset and old-workbook reopening, reference-write failure, and attachment failure after publication followed by reload. Existing edits and pending writes are checked before publication; an attachment failure after publication retains the new workbook. This trades deletion hazards for retained unreferenced storage and does not make concurrent reference writes atomic. The Performance Lab reset path is separate; physical crashes and automated cleanup were not tested.

A separate controlled overlap test pauses candidate readiness, commits an edit to the original workbook, and resumes reset. Chromium, Firefox and WebKit reject publication, remove the candidate head, and retain the edit after reload. The test checks a committed edit at one timing; it does not establish safety for every draft, concurrent tab or interruption timing.

When a scene change is rejected while a scene operation is busy, routing now restores the active scene hash and displays a wait message. A controlled reset/navigation overlap passes in Chromium, Firefox and WebKit, checking the selector and URL before reset completes and the selected workbook after reload. It does not cover every navigation or browser-history sequence.

Scene load success or failure no longer replaces a developer page selected while loading. Six controlled Chromium, Firefox and WebKit cases verify the API page, title, hash and return to the correct spreadsheet for both outcomes. Scene completion also derives the document title from the active developer route; reset-to-plugin overlap is tested separately. These tests do not cover every browser-history sequence.

The combined scene and startup-recovery run passed 110 of 111 cases; Firefox timed out after five seconds while a saved scene still displayed “Opening…”.
