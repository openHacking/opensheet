# Performance Lab protocol

Clean-commit capacity checks (2026-11-12): two sequential Chromium runs against commit `1a2cdb2` failed the 1m threshold in their first round, with edit P95 49.9/81.8 ms, scroll P95 67.2/39.5 ms and restore 282.4/451.9 ms. Both verified the served files against the local build and recorded a clean source tree. The [first](../benchmarks/capacity-1a2cdb2-2026-11-12-1m-failed.json) and [repeat](../benchmarks/capacity-1a2cdb2-2026-11-12-1m-repeat-failed.json) are retained. Other desktop and simulator processes were active on the shared host; this does not establish the cause. Both failed the 33 ms scroll threshold, and neither completed the remaining rounds. Power mode and total process memory were not recorded. The earlier passing result below predates the current engine change and does not override these failures.

An additional [instrumented run](../benchmarks/capacity-1a2cdb2-2026-11-12-traced.json) also failed in round one with scroll P95 35.0 ms, edit P95 60.2 ms and restore 1,951.8 ms. Among 300 scrolls, 19 exceeded 33 ms; their mean viewport-fetch time was 35.4 ms versus 12.4 ms for the others, while mean frame waits were 4.5 versus 6.2 ms. The recorded Worker reads in both groups were page-cache hits, with no observed misses; callbacks and phase timings can overlap and must not be added. Instrumentation and shared-host scheduling affect these observations, so they do not establish a root cause or prove a code regression. The source tree had documentation/evidence changes, while served assets were checked against the local production build.

A subsequent [paired search-change experiment](../benchmarks/capacity-search-paired-2026-11-12.json) used the same production-preview page with its engine Worker replaced by esbuild bundles of current source or a reconstructed pre-search-page-reuse variant. Two fresh contexts per variant ran in alternating order on AC power, and all four runs passed three 1m rounds with 28,009 viewport checks per round. Control/current scroll P95 ranges were 19.0–20.8/19.2–22.4 ms. The served page and assets matched 11 local build files at the start, but both replacement Workers differ from the Vite production Worker. This limited, instrumented, single-host experiment did not reproduce the failures or establish their cause; it does not replace a passing uninstrumented run of the actual committed Worker.

The [paired harness](../scripts/capacity-search-paired.mjs) was formatted after that report was captured; its current file bytes therefore differ from the recorded source fingerprint.

An uninstrumented [production-Worker repeat](../benchmarks/capacity-1a2cdb2-2026-11-12-post-paired.json) then passed all three 1m rounds: edit P95 33.2/34.4/33.2 ms, scroll P95 19.6/19.3/19.3 ms, and restore 199.7/164.3/132.0 ms. The served files matched the local build, whose fingerprint matched the failed runs. The worktree contained diagnostic evidence and scripts; the run records a dirty source tree and is not a clean-commit measurement. This pass does not explain or erase the earlier failures, and the host, power-mode and memory limitations still apply.

Request counts are not physical disk reads; page size is an estimate, not a process-heap bound. The data is from one concurrent, instrumented development-server run per engine, not a production benchmark.

## Workload and budget

The deterministic workload uses 100 columns, 60% finite numbers, 30% 32-byte ASCII strings and 10% booleans. Zero and false count as populated. A stateless fixed-seed generator permits full verification without retaining an extra fixture. Formulas, per-cell styles and XLSX conversion are separate workloads.

Default application budget: 256 MiB. IndexedDB stores binary cell pages and tagged UTF-8 JSON metadata/indices, so the ledger counts the byte lengths of the actual stored application payloads. IndexedDB key/engine filesystem overhead belongs to the separately reported browser usage estimate. Budget checks include encoded data, metadata, history, manifest and temporary records. The UI also reports `navigator.storage.estimate()` origin usage and quota, which are estimates shared with other same-origin storage. Before starting, the application budget may not exceed 80% of estimated remaining quota. If estimates are unavailable, the UI says unknown and still enforces the application budget. A real quota error stops probing immediately.

Pages use typed value columns, offset runs/bitmaps, string arenas/dictionaries and bit-packed booleans; page coordinates implicitly reconstruct stable uint32 row/column identities. Background gzip applies only when it saves at least 10%. Empty unformatted cells have no record. Worker caches reserve at most 64 MiB and the viewport cache at most 8 MiB using page buffer/position/property/dependency reservations. These reservations do not claim to be total process heap. Browser heap measurements cover the main document where available; transient import/export working sets and Worker runtime overhead are separate.

## Measurement and search

A size must pass three rounds. Each round closes and reopens storage, waits for the first fully loaded editable viewport, verifies every populated value in batches, exercises edits across blocks with undo/redo checks, and scrolls to dispersed positions.

After five edit warm-ups, record 100 edits from command start through persisted acknowledgement and completed viewport painting. After 30 scroll warm-ups, record 300 scroll samples through viewport data readiness and painting. Thresholds: edit P95 ≤100 ms, complete scroll frame P95 ≤33 ms, restore ≤10 seconds. Full verification time is reported separately. A failing round can end the candidate early because it can no longer pass all three rounds.

Automatic probing starts at 10,000 cells and doubles until a failure or the 10,000,000-cell dimension boundary. It then refines the passing/failing bracket to 10,000-cell precision. One candidate is retained at a time. Cancellation never counts as a capacity failure or pass. A quota error stops immediately; an application-budget failure can be refined. Maximum means the largest observed passing size in this session, not a universal or mathematically proven maximum. Results retain all tested failures, environment information, thresholds, workload and storage figures.
