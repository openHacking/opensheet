# Conditional formatting: internal model

Status: **prototype only**. Conditional formatting is not yet a persisted, rendered or public feature. DATA-02 remains open.

The internal model in `packages/core/src/conditional-format.ts` accepts ordered rules with half-open ranges, typed numeric, text or formula predicates, visual style overrides and `stopIfTrue`. Earlier rules have higher priority for each style property; lower rules can fill properties that higher rules did not set. A matching stop rule prevents all subsequent rules from contributing. The resolved style is a new object and never changes the base style. Blank, error, Boolean and other mismatched values do not satisfy numeric or text predicates. Text comparison uses JavaScript case folding when `caseSensitive` is false; it is not locale-aware. Formula-derived cell values must be calculated by the caller before evaluation. Conditional number formats, date-specific semantics and other visual effects are not implemented.

The internal validator limits rule count, range dimensions and condition text; it rejects malformed or unknown fields and detaches validated input. A viewport call is bounded by cell count, rule/cell comparisons and a conservative text-work budget. Formula predicates require an asynchronous caller-supplied evaluator bound to an immutable workbook revision and a shared calculation budget. Their references are offset from the rule's top-left cell; only a Boolean true matches, other values and ordinary errors do not, and `#LIMIT!` aborts the whole result. Cancellation returns no partial result. Structural insertion/deletion reuses the validation prototype's range and reference transformations, including explicit cross-sheet references. These limits are provisional engineering guards, not published product limits. Sorting, merging, sheet rename/removal and broader formula/reference behavior remain unverified.

Before exposing the feature, a versioned native schema must preserve rules without allowing older readers to silently discard them. The current schema 3 rejects unknown fields, and the provisional schema 4 work already covers validation; neither the open extensions namespace nor the prototype is a durable enforcement boundary. A separate **internal experimental schema 5** prototype carries both validation and conditional rules. It validates both collections before staging pages, preserves validation when converting back to schema 4, and rejects downgrade when conditional rules are present. It is not a chosen public version, file reader or durable migration. Commands must atomically update rules and history, enforce expected revisions, transform ranges with row/column edits and sorting, and survive cancellation, failure, undo/redo and reopen. Any production migration must retain a verified backup and reject lossy downgrade.

Renderer integration must consume revision-consistent calculated values, distinguish unloaded values from blanks, invalidate appearance after dependent formula changes, and avoid persisting computed appearance over base styles. Visible-cell work, rule indexing, scrolling, large text, cancellation and stale asynchronous results require browser measurements and fault tests. XLSX rules must continue to be reported as unsupported until mapping and independent-reader round trips are verified. The initial numeric/text evaluator does not establish those guarantees.

An internal worksheet-reference rewrite handles explicit formula references on rename or removal, reusing the validation model's formula transformation. It preserves other rules and text literals, validates the rewritten collection and fails without changing its input if the result exceeds the rule limits. It is not connected to worksheet commands or history.

The engine now has an internal staged-viewport bridge that reads cell inputs, calculated values and base styles against a caller-owned immutable head and metadata. One bounded calculation session serves the viewport; values and formula predicates share its budget. The bridge does not publish rules or pin revisions for callers, and a future UI must reject stale results. It enforces position and accumulated text limits, reuses the current staged cell during its calculation, and temporarily retains scalar inputs for formula predicates within that viewport. Formula cells are excluded because cycle results depend on traversal context. The initial read also reuses one most-recent page when its estimated `ColumnPage.bytes` is at most 1 MiB; larger pages are decoded but not retained for the next cell. Both temporary structures are additional to the configured cache reservation, including when it is zero; estimated bytes are not a process-memory bound. Nothing is retained across viewport calls, and peak memory remains unmeasured.
