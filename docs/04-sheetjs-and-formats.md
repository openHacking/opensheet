# SheetJS and table formats

> Design notes, not a claim of implemented functionality. See [implementation status](implementation-status.md) and the [current API](api.md) for supported behavior.

## Ownership and supported fidelity

SheetJS reads/writes file containers; OpenSheet owns the editable model and UI. The adapter accepts structurally compatible SheetJS workbooks without depending on the SheetJS runtime. The demo pins CE 0.20.3 from its official archive, including lockfile integrity.

Import supports sparse/dense cells, sheet order, scalar values, formulas, imported caches, date systems, dimensions, hidden rows/columns, merges, notes and safe links within explicit limits. Complex styles, charts, images, macros, named ranges and unknown file parts are not guaranteed to survive conversion. Array formulas force read-only behavior. XLSX row heights use points; the adapter converts to and from OpenSheet pixels at 96 pixels per inch and prefers explicit point heights when both SheetJS representations exist. Column widths depend on font metrics: import reports font-derived widths as approximations, and export reports every explicit pixel width as approximate; strict mode rejects those conversions. A zero pixel row height cannot be written by the current XLSX writer and is reported as dropped. See [independent dimension checks](verification.md).

Defined names exposed by SheetJS are not preserved: the import report counts each name, including workbook- and worksheet-scoped entries and built-in names exposed by the parser. Strict import rejects the loss, and the retained report remains available on later export. The count covers the parsed collection, not names the parser fails to expose; malformed collections are rejected.

Import also scans formulas for unqualified ASCII names in workbook or current-sheet scope, and ASCII local names qualified by a known sheet, reporting the first affected cell and formula count per sheet. Name definitions and affected formulas are counted as separate losses. The bounded index retains up to 8,192 distinct scoped names; skipped non-ASCII, invalid-scope or excess names trigger an incomplete-scan warning. The scan excludes quoted strings, function calls, cell references, structured-reference brackets, external workbooks and sheet-qualified workbook-global names; it is not a full formula parser or a complete audit. Named formulas may produce errors after import because the definitions are not preserved.

The object adapter accepts a date-typed formula without a cached value and evaluates it using the workbook date system. The pinned XLSX parser cannot read a synthetic worksheet containing an uncached OOXML date-typed formula and omits that worksheet; the playground rejects the import with its sheet name rather than replacing the current workbook. This case is not repaired automatically, and other parser failures may have different behavior.

When callers parse XLSX with SheetJS before calling `fromSheetJS`, enable `sheetStubs: true`: otherwise SheetJS can omit formula cells that have no cached result. The playground file Worker explicitly enables this option; its existing `cellStyles: true` also generates stubs in the tested SheetJS version. Formula stubs' synthetic values are not stored as calculation caches; the formula is evaluated normally.

The IndexedDB workbook is the source of truth after editing; native OpenSheet WorkbookFile documents are interchange data. Keeping an original file is a separate host responsibility. Do not merge arbitrary original workbook parts and claim lossless XLSX patching.

## Compatibility reports

Conversions return reports of supported entries, approximations, dropped features and blockers. Show meaningful summaries and detailed locations; aggregate repeated issues to avoid unbounded report memory. Strict mode rejects detected incompatibilities using complete summary totals, including issues omitted by the detail cap, but cannot guarantee preservation of unexposed file parts. Details retain at most 200 groups, keyed by code, sheet, feature, action and severity; repeated occurrences retain the first address and a count. `omittedIssueOccurrences` counts occurrences not represented in those groups. Subsequent exports retain aggregated import counts and summarize truncated original losses.

XLSX export reports literal empty-string cells as an interoperability approximation: a tested LibreOfficeDev save removed such a cell, which can change `COUNTA` results. The exported XLSX initially contains the empty string; the warning describes a possible later round-trip loss, and strict mode rejects it. This observation does not establish behavior for every spreadsheet application or version.

For blank cells with hyperlinks, the adapter emits an explicit General format so the pinned SheetJS writer includes the hyperlink without turning the blank into empty text. A tested LibreOfficeDev save subsequently removed such hyperlinks, including from a blank cell with a note. Export therefore reports a potential round-trip approximation and strict mode rejects it; behavior in other readers remains unverified.

Imported formula caches are marked and expire after edits. Export avoids potentially stale formula results and requests external recalculation where appropriate. Real Excel, WPS and LibreOffice acceptance needs independent testing.

Import reports bracketed external-workbook and structured-table references in formulas as unsupported. Their formula text is retained, but OpenSheet does not evaluate those references or fetch external workbook data. Strict mode rejects the detected cases. This check does not establish detection of every unsupported formula or file feature.

Import also reports function-call names absent from the same registry used by formula help. Quoted text and quoted sheet names are excluded, and supported OOXML future-function prefixes are recognized. The scan is not a full formula compatibility proof: unsupported syntax, argument modes and runtime errors may still require separate checks.

For supported formulas whose exponentiation or negation may have different precedence, import and export add explicit parentheses to preserve the source calculation profile. If a formula cannot be safely parsed and round-tripped, its text is retained and the adapter reports a possible difference; strict import rejects that approximation. Detection is conservative and may normalize harmless parenthesized cases. See [formula reader findings](formula-reader-findings.md) for evidence and remaining limits.

Export also warns when the serialized formula has 8,192 or more UTF-16 code units excluding the leading equals sign. This is a conservative interoperability warning based on the tested LibreOfficeDev build, which returned errors for long synthetic addition formulas; it does not prove a universal limit. See [independent verification](verification.md).

When `bookFiles: true` supplies raw XLSX parts, the adapter imports row-only, column-only and combined frozen panes when a single default worksheet view has canonical, unambiguous relationships and its first scrolling cell matches the freeze boundary. It accepts an explicit set of neutral view attributes emitted by the tested LibreOffice version; detected selected tabs and non-default selections are reported as dropped. Split panes, other unsupported or ambiguous frozen views are also reported; strict mode rejects these losses. Without raw parts the object-level adapter cannot detect or import panes. `writeXlsx(file, XLSX)` also exports simple frozen panes with the injected SheetJS writer. It verifies generated worksheet relationships and views before patching them; freezes covering an entire axis, archives over 20 MiB, and archives that are not stored ZIPs fall back to a loss report (strict mode rejects them). SheetJS generates the original archive before that size check, and repacking uses additional memory. The object-only `toSheetJS` still reports freezes as dropped. This inspection is not a complete audit of worksheet views or every XLSX feature.

OpenSheet permits sheet names beginning or ending with an apostrophe and the name `History`; the pinned SheetJS XLSX writer rejects them. `toSheetJS` reports each affected sheet as blocked, and `writeXlsx` refuses the export with rename guidance before calling the writer. `unsupportedXlsxSheetName(name)` exposes the pinned writer's sheet-name restrictions, and `XLSX_SHEET_NAME_MESSAGE` supplies the associated guidance. The playground uses them before creating a workbook snapshot or export Worker; direct `writeXlsx` still scans cells for a complete compatibility report but does not retain a second worksheet full of exported cells when rejecting. It does not rename sheets or rewrite references automatically. After renaming, other compatibility warnings may still require review.

OpenSheet allows text cells of up to 32,768 UTF-16 code units, but the pinned XLSX writer rejects text above 32,767. Export reports those cells as blocked, with a count and first location per sheet, and the byte writer refuses before calling SheetJS. Shorten the affected cells or use the native format to retain them. Report details remain subject to the 200-group cap. This boundary concerns literal text cells; formula and note limits in other readers have not been established by this check.

During byte export, after the first overlong text cell is found, already constructed SheetJS cell tables are released and later cells are scanned for the report without retaining their exported representations. The input snapshot and report scan remain necessary, and a late blocker can still reach the normal conversion peak before rejection.

When the report's 200-group detail cap is full, a new blocked group replaces a non-blocked group if one is available. Totals still include displaced occurrences; if all retained groups are already blocked, later groups can be omitted. For oversized text, the byte-export error in report mode separately identifies the first affected sheet and cell even when its report detail is omitted. Strict mode returns the capped compatibility report with its standard strict-check error.

When raw worksheet parts are available, detected selected tabs and non-default active-cell selections are reported even on sheets without frozen panes. The inspection is conservative and does not guarantee detection of every non-default worksheet view.

For a generated XLSX larger than 20 MiB, the writer also tries a compressed serialization and returns it when smaller. Compression can require another full serialization and does not guarantee that the file fits the playground import limit; frozen panes that exceed the repacking limit remain reported as lost.

Literal text shaped like `_x0041_` can be interpreted as an XLSX escape by SheetJS on a later read. Export reports this risk in sheet names, cell text, formulas, number formats, notes and link targets; strict mode rejects it. With `bookFiles: true`, import conservatively scans selected raw XML and relationship parts for this pattern before conversion and reports ambiguous parts, including patterns built from numeric XML character references and common BOM-less UTF-16 encodings. It also reports if the scan's work budget is exhausted. Reader behavior differs: the tested LibreOfficeDev build preserved the literal cell text. The scan does not distinguish intentional escapes from literal text, restore the original value, or cover every encoding and part. Without raw parts this import check is unavailable.

Unpaired UTF-16 surrogates in sheet names, cell values, formulas, number formats, notes and links are reported as approximations on XLSX export; strict mode rejects them. The pinned SheetJS writer/reader replaces tested unpaired surrogates with U+FFFD. Valid surrogate pairs such as emoji do not trigger this warning. Native OpenSheet formats preserve unpaired surrogates.

Some control characters are written as XLSX escape sequences and may appear as literal escape text in other applications; the tested writer/reader replaces U+FFFE with U+FFFD. Export reports this as an approximation; strict mode rejects it. Line feeds and tabs are not included in that particular warning.

The playground prepares XLSX in a Worker after creating a workbook snapshot. If the workbook changes while preparing or reviewing the export, start the export again. The Worker is stopped after 120 seconds; snapshot creation and transferring it to the Worker can still pause the main thread and consume additional memory. Before downloading an XLSX larger than the playground's 20 MiB import limit, the compatibility dialog warns that it cannot be reopened in the playground.

## Browser import pipeline

The demo checks file size, transfers bytes to a Worker, verifies ZIP contents, parses, adapts, validates and atomically loads the canonical WorkbookFile. The XLSX/CSV input limit is 20 MiB and the file-adapter Worker timeout is 20 seconds. Native JSON/binary input instead uses page-staged imports in the storage Worker, cancellation and progress-based timeouts, with storage/per-page bounds rather than the 20 MiB limit. On errors, cancellation or timeout the previous workbook must remain intact.

ZIP recognition uses the leading record signature regardless of extension; `.xlsx` requires a ZIP container. The demo accepts single-disk stored/deflated archives with at most 10,000 entries and 200 MiB declared expansion. It checks directory/local names, sizes, flags, descriptors, nonoverlapping complete record coverage and checksums. Deflate entries are streamed through `DecompressionStream('deflate-raw')` with 1 KiB input chunks; actual output must match the declared size and CRC before SheetJS receives the file. Expanded chunks are discarded during verification. ZIP64, encryption, self-extracting prefixes, unknown compression and extra unindexed records are rejected rather than passed unchecked. Signed and unsigned data descriptors are supported.

These checks belong to the playground file Worker, not the object-level SheetJS adapter. They add a verification pass before SheetJS's own decompression/materialization. Native decoder buffering and parsed XML/object overhead do not establish a hard browser memory ceiling; Worker timeout is not process isolation. Server integrations still need process isolation and actual CPU/memory limits. Formula length, depth, range visits and workbook dimensions also have resource budgets. The ZIP record contract follows [PKWARE APPNOTE](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT).

## Dates and numeric values

Preserve 1900/1904 systems. Test boundary serials, fractions and timezone semantics rather than treating spreadsheet serials as JavaScript epoch timestamps. Long IDs and integers beyond safe precision should remain text. Current display formatting is a subset, not the full Excel SSF language. The supported time profile includes `h:mm`, `hh:mm`, optional `:ss`, and those patterns following `yyyy-mm-dd` with a space or `T`. Values are rounded to the displayed minute/second; negative times display `#####`. LibreOffice CSV differs at a tested midnight rounding boundary and at the fictitious 1900 leap day; Excel validation remains open.

For SheetJS `t: d` inputs, JavaScript `Date` objects use their UTC calendar fields, matching SheetJS `cellDates` results independently of the host timezone. Hosts constructing `Date` objects from local fields must account for this contract. String inputs accept `YYYY-MM-DD` and ISO date-times with optional seconds, up to three fractional digits and optional `Z` or `±HH:MM`. A string without an offset preserves its stated calendar fields; an explicit offset is normalized to UTC before conversion. Invalid calendar dates, ambiguous locale strings and malformed offsets are rejected. These conversions are reported as approximations; normal XLSX numeric date serials do not use this path.

## Text exports

`exportRange(file, { sheetId, range, format, options })` returns text, diagnostics and required LaTeX packages where applicable. It reads model data rather than Canvas pixels.

- LaTeX supports tabular, booktabs and supported merged cells; escape ordinary text and report package requirements. There is no TeX/PDF compilation or source import.
- Markdown uses the first row as a header, escapes pipes and line breaks, and reports unsupported merges.
- HTML uses semantic tables, escaped text and a style allowlist rather than arbitrary scripts.
- CSV/TSV supports quotes, multiline text, BOM and CRLF. Safe mode (the default) prefixes an apostrophe to text beginning with tab, carriage return, line feed, NUL, or an ASCII/full-width `=`, `+`, `-`, `@` after optional whitespace. Numeric negatives are not changed. Explicit `options.safe: false` preserves text without this transformation and should be used only when the consumer handles untrusted values appropriately. Apostrophe handling varies by spreadsheet application; saving and reopening a CSV may remove escapes, so this is not a universal formula-injection guarantee. See [OWASP CSV Injection](https://community.owasp.org/attacks/CSV_Injection).
- Formulas normally export as calculated values. To emit formula expressions, explicitly set `options: { formulas: 'preserve', safe: false }`; requesting preservation without `safe: false` fails. This emits executable formulas and leaves formula-like text unescaped. References are not rebased for the exported range, and CSV/TSV cannot carry omitted cells, other sheets or a workbook's metadata. Formula syntax and behavior vary among readers; use this only for a trusted workflow with a known consumer.

`streamExport(book, config)` reads bounded asynchronous batches without materializing the entire workbook; `exportRange` remains the explicit materialized WorkbookFile convenience. XLSX remains a SheetJS materialization boundary and does not establish engine capacity. Exports cutting through a merged range are rejected. HTML grid previews are not actual TeX rendering. Future formats should remain separate adapters instead of expanding core responsibilities.

## References

[SheetJS cell model](https://docs.sheetjs.com/docs/csf/cell/), [formulas](https://docs.sheetjs.com/docs/csf/features/formulae/), [dates](https://docs.sheetjs.com/docs/csf/features/dates/) and [installation](https://docs.sheetjs.com/docs/getting-started/installation/nodejs/) describe the upstream format contracts.

Unknown numeric error codes on import and unsupported OpenSheet error strings on XLSX export are converted to `#VALUE!` with an `ERROR_CODE_APPROXIMATED` issue; strict mode rejects the conversion. Malformed boolean values and non-integer error codes are rejected. Formula cells without cached values remain valid.

Explicitly empty cell notes are retained in native storage and passed to the XLSX writer. The SheetJS writer omits an explicitly empty hyperlink tooltip; export reports `EMPTY_LINK_TOOLTIP_DROPPED`, and strict mode rejects this loss.

On import, numeric/formula cells whose number-format code is outside the conservative `isSupportedNumberFormat` display profile receive a `NUMBER_FORMAT_APPROXIMATED` issue. The original format code remains stored for re-export; strict mode rejects the detected approximation. The profile is not a guarantee of full Excel formatting or identical rounding in every reader.

The fixed English month/day profile also supports `m/d/yy`, `mm/dd/yyyy` and combinations of one/two-digit month/day with two/four-digit years, optionally followed by the supported time patterns. Serial zero in the 1900 system displays the Excel-compatible fictitious date `1900-01-00`; serial 60 displays `1900-02-29`. This is a fixed display convention and does not follow the host locale. LibreOffice’s locale-specific short-date rendering can differ.


A synthetic numeric display comparison with LibreOfficeDev is recorded in [the numeric-format report](../benchmarks/numeric-format-2026-10-31.json). Positive and negative grouped currency, percentage and selected rounding values agreed in 14 of 16 observations across the two workbook date systems. For `-0.001` with `$0.00`, OpenSheet shows `-$0.00` while that reader's CSV shows `$0.00`. This is one reader and locale, not an Excel or visual compatibility guarantee.
