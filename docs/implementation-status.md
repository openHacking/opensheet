# Implementation status

The default engine is a Worker-backed IndexedDB workbook with 64 × 32 blocks, binary typed-column pages with uint32 sheet-local identities, bitmap/run positions, string arenas/dictionaries, selective background gzip and run-encoded axis metadata, a 64 MiB Worker cache reservation and an 8 MiB viewport cache reservation. The former 200,000 total-cell limit and whole-snapshot node-count limit are removed. Row, column, sheet, text, read-batch and operation resource limits remain.

All playground scenes, the editor, formula bar, toolbar, plugins, React/Vue wrappers, file adapters and examples use asynchronous workbook I/O. Changes persist locally and scene identifiers restore the corresponding workbook on refresh. The Performance Lab uses a separate database and deterministic mixed data; see [its protocol](performance.md).

Supported behaviors include typed values, cross-sheet formulas, formats, merges, frozen panes, search, atomic replacement, filters, disk-backed sorting, structural reference updates, atomic command batches, persistent undo/redo and multi-tab single-writer coordination. Revisions are published only after storage commits; staged failures and cancellation preserve the previous revision. Recovery removes orphan records left by interrupted workers.

WorkbookFile schema 3 is the sole public JSON shape; there is no public toSnapshot. Native JSON/binary Blob and stream imports stage bounded pages atomically. toJSON returns every occupied cell and intentionally materializes the complete JSON document. Native exports traverse occupied pages and omit unused styles. JSON and table output can be streamed by input batches; Blob download output still consumes memory. SheetJS XLSX conversion is materialized and reports unsupported features. Complex styles, charts, macros, external/named references, array formulas and full Excel compatibility remain outside supported behavior. Formula-result sorting uses values calculated from the pre-sort transaction stage; see [sorting behavior and remaining acceptance](formula-sort-design.md).

Validation rules, conditional formatting and named ranges have internal prototypes only. They are not public, persisted workbook features; the validation and conditional-format prototypes do not enforce writes or render rules. XLSX compatibility reports can flag unsupported rules, but do not import or preserve them. See the [capability inventory](capabilities.md) for the boundaries and evidence.

Ordinary mutations use a 32 MiB traversal planning budget (512 reserved bytes per visited cell), a 32 MiB working-set/undo delta budget, and single read batches are limited to 16,384 cells. Large structural operations and sorting stage on disk but remain subject to the undo and total storage budgets. Formula evaluation has a 128-dependency-depth and 10,000,000-reference work budget. Metadata for up to 100,000 rows remains resident. Worker and viewport cache reservations do not bound total browser heap; the synchronous snapshot reader's formula-result cache has a 4 MiB estimated reservation; this does not bound total heap.

Browser Workers, IndexedDB, Web Locks and BroadcastChannel are required for an editor workbook. Pure range/file readers, schemas, formulas and file adapters can be used in Node; a custom editable runtime must provide compatible Worker, storage and coordination facilities. There is no supported Node persistence adapter; see [Node and headless use](node-usage.md). Pre-0.1.1 persisted-engine layouts and native schema versions other than 3 are unsupported; an existing unversioned directory head is accepted and receives the current marker on its next successful publication. No general persisted-engine migration or synchronous workbook API compatibility is provided.

Stable identity lookup uses a chunked sequence tree with sparse reverse indexes. Scalar edits reuse unchanged metadata and update only touched pages/directory shards; reference retention and garbage collection are incremental. Cached formula dependencies use an interval index, with transitive range invalidation. Structural edits preserve ordinary page coordinates and rewrite candidate formula pages. Candidate discovery still scans the resident directory; axis arrays remain resident and structural edits can copy them. Formatting/merge/used-range metadata and formula-heavy workloads have their own costs, so binary value-storage wins are not claims of constant time for every spreadsheet operation.

Agent APIs provide lightweight metadata, axis windows, selected cell fields, revision-bound occupied-cell cursors and command envelopes. Import/export, file adapters, plugins and React/Vue initialFile use WorkbookFile consistently; no historical compatibility layer or version-suffixed namespace is retained. See [API](api.md), [format](storage-format.md) and [measurements](performance.md).

See the [capability evidence inventory](capabilities.md) for implemented/partial/unverified/planned states and the [provisional workload profile](workload-profile.md) for acceptance tasks and device requirements.

Formula function names, arities and signatures now share an immutable runtime registry; [formula semantics](formulas.md) records verified rules and remaining compatibility gaps. Historical local strict 1m runs include both passes and failures; they do not establish current-commit, Windows or release acceptance. See [performance](performance.md) for results and limitations.
